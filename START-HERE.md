# SmakHub 03: починаємо з ЛР2, завершуємо робочий продукт до захисту ЛР3

## Що зроблено в цій версії

Єдине джерело вихідного коду — SmakHub 2. Старі SmakHub 3, 4, 5 та інші папки
не використані і не змінені. Нумерація 03, 04 тощо — контрольні версії розвитку,
а не додаткові лабораторні курсу.

- Працює локальний пошук восьми карток за назвою, інгредієнтами та фільтрами.
- Пошукові параметри записуються в URL; працюють скидання і повернення назад.
- Є інтеграційний код Supabase Auth: реєстрація, вхід, перевірка поточного
  користувача на account.html, вихід. До заповнення config.js мережеві виклики
  не виконуються; інтерфейс чесно показує недоступність сервісу.
- Є початкова SQL-схема з RLS, готова для виконання в НОВОМУ Supabase-проєкті.
- scripts/build.cjs збирає тільки публічні файли в dist/.

## Найпростіший стек

| Потреба | Рішення | Що більше не треба підтримувати окремо |
|---|---|---|
| Сторінки | Наявні HTML/CSS/JS + статичний хостинг | Обов’язковий перехід на React/Bootstrap |
| База даних | Supabase Database (PostgreSQL) | Встановлення й адміністрування окремого PostgreSQL-сервера |
| Акаунти | Supabase Auth | Власне зберігання паролів, bcrypt/JWT-сервер |
| Фото користувачів | Supabase Storage на наступному етапі | Cloudinary + Multer як окремі компоненти |
| Звернення та пошта | Supabase Edge Function + поштовий провайдер | Постійний Express-сервер лише заради форми |

PostgreSQL — рушій бази даних, Supabase — платформа, яка ним керує. Це не
відмова від PostgreSQL, а спрощення способу його використання. Supabase не
реалізує автоматично модерацію, каталог чи адмін-панель: цю логіку пишемо ми.

## Що зробити зараз: три практичні кроки

### 1. Опублікувати інтерфейс

Варіант для власного загальнодоступного посилання: https://dash.cloudflare.com/

1. Увійти або зареєструвати акаунт.
2. Workers & Pages → Create application → Pages → Direct Upload / Drag and drop.
3. Завантажити папку dist або підготовлений smakhub-03-upload.zip.
4. Відкрити отримане посилання pages.dev і перевірити головну та каталог.

Це публікує інтерфейс, а не створює БД. Direct Upload зручний для першої публікації.
Для автоматичних публікацій через Git згодом потрібно створити окремий Pages-проєкт
із Git integration: змінити тип наявного Direct Upload-проєкту не можна.
https://developers.cloudflare.com/pages/get-started/direct-upload/

### 2. Створити проєкт Supabase

1. Відкрити https://supabase.com/dashboard і зареєструватися/увійти.
2. Створити організацію та новий проєкт SmakHub. Обрати доступний регіон у Європі.
   Почати з Free, перевіривши поточні ліміти; платний тариф без рішення не вмикати.
3. Зберегти пароль БД у менеджері паролів. Не вставляти його в HTML або чат.
4. У SQL Editor один раз виконати supabase/001_initial.sql. Він створює profiles,
   recipes, favorites і contact_messages. Порожня схема ще не наповнює каталог.
5. Скопіювати Project URL та Publishable key з підключення/API Keys проєкту.
6. Внести ці ДВА ПУБЛІЧНІ значення у js/config.js. Не використовувати secret key
   або service_role. URL і publishable key можна передати мені для налаштування.
7. Authentication → URL Configuration: Site URL = адреса сайту; додати точний
   URL account.html до дозволених redirect URLs. Не ставити довільний wildcard.
8. Перезібрати dist і оновити сайт. Перевірити реєстрацію → лист → вхід → вихід.

Альтернатива ручному SQL: підключити Supabase у каталозі плагінів ChatGPT,
щоб я міг працювати з проєктом через надані права. Самого акаунта без підключення
недостатньо для доступу з цієї розмови.

### 3. Налаштувати пошту

Є ДВІ різні задачі:
- Auth-листи: підтвердження адреси й відновлення пароля — Supabase Auth + custom SMTP.
- Контактна форма: повідомлення команді — окрема Edge Function, збереження в БД,
  виклик поштового API/SMTP та запис статусу доставки.

Вбудована пошта Supabase призначена для обмеженого тестування; для довільних
адрес потрібен власний SMTP/Send Email hook. Не вимикати підтвердження адрес
на публічному сайті тільки заради демонстрації. Документація:
https://supabase.com/docs/guides/auth/auth-smtp

Для поштового провайдера потрібен акаунт; для повноцінного відправника зазвичай
потрібне підтвердження домену. Адресу підтримки обирає команда. Секрет SMTP/API
зберігається у Supabase Secrets, не в js/config.js. Зараз форма контактів НЕ надсилає дані.

## План ДО захисту третьої роботи

| Версія | Роботи | Критерій готовності |
|---|---|---|
| 03 — старт | Хостинг, локальний пошук, підготовка Auth і БД | Сайт відкривається за URL; пошук працює; після підключення проходить вхід |
| 04 — дані | Повний вміст 8 рецептів, початкове наповнення БД, читання каталогу/API, пошук за інгредієнтами в БД | Кожна картка відкриває свій запис, дані переживають оновлення |
| 05 — автор | Кабінет, улюблене, форма нового рецепта, редагування своїх чернеток, Storage для фото | Два користувачі не бачать і не змінюють чужі приватні дані |
| 06 — модератор | Ролі, черга pending, схвалення/відхилення з причиною, повторне подання | Автор не може сам опублікувати рецепт; у каталозі тільки published |
| 07 — звернення | Edge Function з перевірками та захистом від спаму, БД, листи підтримці | Є реальний запис і перевірена доставка, помилки не маскуються успіхом |
| 08 — здача | Усі CSS-вимоги ЛР3, браузери, права доступу, HTTPS, GitHub, скриншоти й звіт | Наскрізний сценарій працює на розгорнутому сайті |

Це черговість, а не вимога робити етапи в різні дні. Мета — завершити основний
сценарій до ЛР3, залишивши ЛР4 для її конкретних JS-вправ і вдосконалення.
Для повної відповідності всім майбутнім пунктам ЛР1 окремо потрібні оцінки,
коментарі, uk/en, відновлення пароля, вподобання, рекомендації та керування
категоріями/користувачами. Їх не слід називати готовими до реалізації й тестів.

## Обмеження саме поточного коду

- Каталог фільтрує наявні картки в браузері; це ще НЕ читання з Supabase.
- Повна сторінка поки одна — борщ із ЛР2. Інші картки ще ведуть на цей шаблон.
- Склад для фільтра — початкова довідкова розмітка. У версії 04 він має формуватися
  з того самого запису БД, що й повна сторінка рецепта.
- Auth потребує реального проєкту та конфігурації; локальні тести не замінюють
  перевірку email-доставки, сесій і RLS у віддаленому Supabase.
- SQL не відкриває запис рецептів користувачам і доступ до звернень. Ці права
  додаються тільки разом із workflow автора/модератора й Edge Function.
- У початковій схемі паролів немає: ними керує Supabase Auth.

## Запуск і збірка

    node scripts/build.cjs

Готова папка для статичного хостингу — dist/. У ній немає SQL, тестів і документації.
Для роботи Auth використовувати HTTP/HTTPS, а не file://. Без конфігурації сайт
показує недоступність реєстрації, а не вигадане створення акаунта.

## Що потрібно від користувача

Облікові записи/вхід у сервіси, вибір тарифу та оплата (якщо знадобиться),
підтвердження email/домену, права запису до командного GitHub, вибір першого
адміністратора. Код і файли конфігурації я можу готувати до підключення акаунтів.
